# Документация проекта PostDesk

Черно-белая версия для печати.  
Дисциплина: React + Redux.  
Формат: индивидуальный проект.  
Проект: PostDesk, менеджер публикаций на React, Redux Toolkit и REST API.

## Страница 1. Общая информация о проекте

PostDesk является учебным React-приложением, которое показывает полный поток работы с данными в современном frontend-проекте. Приложение построено как небольшой менеджер публикаций: пользователь может загрузить список постов из API, просмотреть их, отфильтровать, создать новый пост, изменить существующий пост и удалить ненужный пост. Основная цель проекта - продемонстрировать понимание React-компонентов, маршрутизации, Redux Toolkit, асинхронных операций и обработки пользовательских состояний.

Проект реализован как одностраничное приложение. Навигация построена через React Router. В приложении есть пять основных страниц:

1. Dashboard - главная страница со статистикой и последними публикациями.
2. Posts - список публикаций, поиск, фильтрация, переход к редактированию и удаление.
3. Create - форма создания новой публикации.
4. Authors - список авторов, загруженный из API.
5. Docs - краткое встроенное описание архитектуры проекта.

В качестве внешнего источника данных используется JSONPlaceholder. Этот API подходит для учебного CRUD-проекта, потому что предоставляет ресурсы posts и users, а также поддерживает демонстрационные POST, PUT и DELETE запросы. Важно понимать, что JSONPlaceholder не сохраняет изменения на сервере навсегда. Поэтому приложение после успешного POST добавляет созданный объект в Redux state локально, а после DELETE удаляет объект из Redux state. Это нормальное поведение для данного учебного API.

Приложение удовлетворяет ключевым требованиям экзамена:

- используется React;
- есть маршруты и несколько страниц;
- используется Redux Toolkit;
- настроен `configureStore`;
- логика разделена на slice-файлы;
- данные читаются через `useSelector`;
- действия запускаются через `useDispatch`;
- асинхронная логика реализована через `createAsyncThunk`;
- есть работа с REST API;
- реализованы GET, POST, PUT и DELETE операции;
- есть CRUD функционал;
- есть поиск и фильтрация;
- есть loading, error и empty состояния.

Пользовательский интерфейс сделан в спокойном рабочем стиле. На страницах нет лишнего маркетингового контента: первое действие пользователя связано с реальной работой приложения. Такой подход подходит для учебного проекта, потому что преподавателю проще проверить архитектуру, Redux flow и функциональность.

## Страница 2. Структура проекта и маршрутизация

Структура проекта организована по функциональным слоям. Такой подход помогает быстро найти нужную часть кода и объяснить проект на защите. Главная структура находится в папке `src`.

```text
src/
  components/
  hooks/
  pages/
  redux/
    store.js
    slices/
      postsSlice.js
      usersSlice.js
  routes/
    AppRoutes.js
  services/
    apiClient.js
    postsApi.js
    usersApi.js
  utils/
    posts.js
  App.js
```

Папка `components` содержит переиспользуемые компоненты интерфейса. Например, `Layout` отвечает за общий каркас приложения и навигацию, `PostCard` отвечает за отображение одной публикации, `PostForm` используется для создания и редактирования, `StateBox` показывает loading/error/empty сообщения, а `PostFilters` содержит поиск и фильтр по автору.

Папка `pages` содержит страницы маршрутов. Каждая страница отвечает за конкретный экран приложения. Например, `PostsPage` показывает список постов, `CreatePostPage` открывает форму создания, `EditPostPage` открывает форму редактирования, `UsersPage` показывает авторов, а `DashboardPage` показывает общую статистику.

Папка `redux` содержит Redux-архитектуру. Файл `store.js` создает store через `configureStore`. В папке `slices` находятся отдельные модули состояния. `postsSlice.js` отвечает за публикации, фильтры, CRUD и async flow. `usersSlice.js` отвечает за список авторов и загрузку пользователей из API.

Папка `services` отделяет работу с API от UI и Redux. Это важно, потому что компоненты не должны напрямую знать URL endpoint-ов. Компоненты вызывают Redux actions, Redux thunk вызывает сервис, а сервис выполняет HTTP-запрос.

Маршрутизация описана в `src/routes/AppRoutes.js`. Основные маршруты:

- `/` - Dashboard;
- `/posts` - список публикаций;
- `/posts/new` - создание публикации;
- `/posts/:postId/edit` - редактирование публикации;
- `/users` - авторы;
- `/documentation` - встроенная документация;
- `*` - страница 404.

Главных страниц для демонстрации пять: Dashboard, Posts, Create, Authors, Docs. Отдельный маршрут редактирования нужен для полноценного CRUD, но логически он относится к разделу Posts.

Компонент `Layout` содержит верхнюю навигацию. Для активного пункта используется `NavLink` из React Router. Это позволяет пользователю понимать, на какой странице он находится. Приложение запускается в `src/index.js`, где подключены `Provider` для Redux и `BrowserRouter` для маршрутов.

## Страница 3. Redux архитектура

Redux Toolkit используется как основной инструмент управления состоянием. Store создается в файле `src/redux/store.js`:

```js
export const store = configureStore({
  reducer: {
    posts: postsReducer,
    users: usersReducer,
  },
});
```

В приложении есть два основных slice:

1. `postsSlice` - состояние публикаций.
2. `usersSlice` - состояние авторов.

Состояние `postsSlice` содержит:

- `items` - массив публикаций;
- `loading` - состояние загрузки списка;
- `loaded` - флаг, что первая загрузка уже выполнялась;
- `submitting` - состояние отправки формы;
- `deletingIds` - список id, которые сейчас удаляются;
- `error` - текст ошибки;
- `filters` - объект фильтров поиска и автора;
- `lastSync` - время последней успешной загрузки.

Такое разделение делает интерфейс предсказуемым. Например, если `loading = true`, можно показать loading state. Если `error` содержит текст, можно показать error state. Если `items` пустой и загрузка завершена, можно показать empty state.

Состояние `usersSlice` содержит:

- `items` - массив пользователей;
- `loading` - состояние загрузки;
- `loaded` - флаг первой загрузки;
- `error` - текст ошибки.

В проекте применяются стандартные инструменты Redux Toolkit:

- `configureStore` - создание единого Redux store;
- `createSlice` - создание reducer и actions;
- `createAsyncThunk` - асинхронные запросы;
- selectors - функции чтения данных из state.

Компоненты используют `useSelector` и `useDispatch` через короткие wrappers в `src/hooks/useRedux.js`. Это позволяет централизованно импортировать hooks и упрощает структуру компонентов.

Примеры selectors:

- `selectPosts` возвращает весь список публикаций;
- `selectFilteredPosts` возвращает список после поиска и фильтра по автору;
- `selectPostById` находит одну публикацию для страницы редактирования;
- `selectPostStats` считает статистику для Dashboard;
- `selectUsers` возвращает список авторов.

Фильтры находятся в Redux, а не только в локальном состоянии компонента. Это полезно, потому что состояние UI становится частью общей Redux-модели. Пользователь меняет поле поиска, компонент отправляет action `setSearchFilter`, reducer обновляет `state.posts.filters.search`, а `selectFilteredPosts` пересчитывает отображаемый список.

Такую архитектуру легко объяснить на защите: компонент не меняет данные напрямую. Он вызывает dispatch. Action попадает в reducer или thunk. Reducer обновляет state. Компоненты получают новое значение через selector и перерисовываются.

## Страница 4. Async flow и работа с API

Асинхронная логика реализована через `createAsyncThunk`. Это важная часть проекта, потому что экзаменационные требования отдельно указывают наличие async flow. В PostDesk есть несколько async операций:

- `fetchPosts` - GET `/posts`;
- `createPost` - POST `/posts`;
- `updatePost` - PUT `/posts/:id`;
- `deletePost` - DELETE `/posts/:id`;
- `fetchUsers` - GET `/users`.

Общий HTTP-клиент находится в `src/services/apiClient.js`. Он содержит базовый адрес API и проверку ошибок ответа. Если сервер возвращает неуспешный HTTP-статус, создается ошибка, которая затем попадает в rejected state соответствующего thunk.

Файл `src/services/postsApi.js` содержит методы для публикаций:

- `getPosts()`;
- `createPost(post)`;
- `updatePost(id, post)`;
- `deletePost(id)`.

Файл `src/services/usersApi.js` содержит метод `getUsers()`. Такое разделение делает код понятным: Redux-slice отвечает за состояние, service отвечает за HTTP.

Async flow на примере загрузки публикаций:

1. Страница вызывает hook `useInitialData`.
2. Hook проверяет, загружались ли posts и users.
3. Если данные еще не загружены, вызывается `dispatch(fetchPosts())`.
4. Redux Toolkit отправляет состояние `pending`.
5. Reducer ставит `loading = true` и очищает ошибку.
6. Thunk вызывает `postsApi.getPosts()`.
7. После успешного ответа приходит `fulfilled`.
8. Reducer записывает данные в `items`, ставит `loading = false`, `loaded = true`.
9. Компоненты получают новые данные через selectors.

Если запрос завершился ошибкой, приходит `rejected`. Reducer сохраняет текст ошибки в `error`, а UI показывает компонент `StateBox` с типом error и кнопкой Retry.

CRUD flow:

- Create: форма собирает `title`, `body`, `userId`, затем вызывает `createPost`. После успешного POST новый объект добавляется в начало массива posts.
- Read: список posts загружается через GET и отображается на Dashboard и Posts.
- Update: страница edit вызывает `updatePost`. Для исходных API-постов отправляется PUT-запрос. Для созданных в текущей сессии локальных постов используется тот же thunk, но изменение остается локальным, потому что JSONPlaceholder не хранит созданные объекты постоянно.
- Delete: кнопка Delete вызывает `deletePost`. Для API-поста отправляется DELETE-запрос, затем объект удаляется из Redux state.

В приложении отдельно отображаются loading, error и empty состояния. Это видно на страницах Dashboard, Posts, Create, Edit и Authors. Такой подход показывает, что проект учитывает реальные состояния frontend-приложения, а не только успешный сценарий.

## Страница 5. Функциональность, защита и оценивание

Основной пользовательский сценарий:

1. Запустить проект командой `npm start`.
2. Открыть `http://localhost:3000`.
3. На Dashboard увидеть статистику и последние публикации.
4. Перейти на Posts.
5. Использовать поиск по заголовку или тексту.
6. Использовать фильтр по автору.
7. Создать новую публикацию на странице Create.
8. Вернуться в список Posts и увидеть новую запись.
9. Открыть Edit и изменить заголовок или текст.
10. Удалить публикацию через кнопку Delete.
11. Открыть Authors и увидеть список авторов, загруженный из API.
12. Открыть Docs и кратко объяснить архитектуру.

Поиск и фильтрация реализованы на странице Posts. Поле Search ищет совпадения в `title` и `body`. Select Author фильтрует публикации по `userId`. Если после фильтрации ничего не найдено, пользователь видит empty state "Nothing found".

Обработка ошибок реализована на уровне async thunk и Redux state. Если API-запрос завершается ошибкой, текст ошибки записывается в `state.posts.error` или `state.users.error`. UI читает это поле и показывает понятное сообщение. Для загрузки постов доступна кнопка Retry.

Loading state реализован через поля `loading` и `submitting`. `loading` отвечает за начальную загрузку списков, `submitting` отвечает за отправку формы создания или редактирования. Для удаления используется массив `deletingIds`, чтобы можно было заблокировать только конкретную кнопку Delete, а не весь интерфейс.

На защите можно объяснить Redux архитектуру так:

- Store создается в `src/redux/store.js`.
- Posts и users подключены как отдельные reducers.
- Компоненты читают состояние через selectors.
- Компоненты не вызывают fetch напрямую.
- Компоненты вызывают dispatch.
- Async thunk выполняет API-запрос.
- Extra reducers обрабатывают pending, fulfilled и rejected.
- UI реагирует на изменения state.

Соответствие критериям оценивания:

- Работоспособность: приложение запускается, собирается и выполняет основные сценарии.
- Redux архитектура: есть store, slices, selectors, async thunks.
- Функциональность: реализованы CRUD, поиск, фильтр, навигация, состояния.
- Структура проекта: код разделен на components, pages, redux, services, hooks, routes, utils.
- Документация: данный файл содержит печатную документацию минимум на 5 страниц.
- Защита: проект имеет понятный поток демонстрации и объяснимую архитектуру.

Важное замечание для защиты: JSONPlaceholder является fake REST API. Он отвечает на POST, PUT и DELETE, но не сохраняет данные на сервере между перезагрузками. Поэтому созданные записи сохраняются в Redux state только во время текущей сессии. Это ожидаемое поведение выбранного API и нормальный вариант для учебного проекта.
